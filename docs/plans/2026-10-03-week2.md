# Week 2: Split, Dry Run, OCR, Mapping and Analytics

**Goal:** Between Saturday 3 and Friday 9 October, build the issuer split and run the first dry run on the train holdout. Choose the OCR engine for Docker by measured accuracy. Map labels to canonical items. Compute the identity checks and about 12 metrics. Decline banks and insurers with a reason. Report Gates A and B on `dev` and on the dry run, per period kind.

**Why this order:** The dry run needs the split, and its time per document decides whether the 24 October checkpoint fits in one day. So the split comes first and the dry run second. Scanned accuracy is the critical path: 218 of 254 numeric cells, 85.83%, against a gate of 98.0% (`docs/blueprint/12-ingest-review.md`). So the OCR bake-off comes before mapping and analytics. Mapping comes before analytics, because metrics need canonical items. Gates A and B come last, because they are measured over everything else.

**Departures from the week 2 row of `08-revised-plan.md`:** fuzzy matching is conditional (Task 4), there is no blind run (D17), and Gates A and B are reported on `dev` and the dry runs instead of `model_test`, which waits for the checkpoint (D13).

**Spec:** `docs/blueprint/08-revised-plan.md` (week 2 row, Gates, the note after the gates), `docs/blueprint/04-execution-phases.md` 2.4 (the split, dry runs, D18), `docs/blueprint/06-decisions-and-risks.md` 6.1 (D1 to D6, D13, D16 to D18), `eval/corpus/README.md` (rules 1 to 6), `docs/blueprint/14-run-profiles.md` ("Left for later").

## Global constraints

- One branch per task, named for the task. One or more commits per task, authored as the owner, with no trailers (see the repository's working rules).
- `make test`, `make lint`, `make typecheck`, `make docs-check` and `make corpus-check` pass by exit code before every commit, and the output is read.
- Tests come first for anything that parses or computes.
- A specialist implements each task and a different one reviews it. `code-reviewer` reviews every diff. `ml-engineer` also reviews evaluation work, and `solutions-architect` anything that crosses packages. Critical and Important findings are fixed and re-reviewed.
- Nothing runs against `model_test` or `blind` (D13, D17).
- Every look at the holdout is logged through `fra_core.split.holdout_for_scoring`. Nobody opens a holdout document to debug it: failures are recorded as classes and fixed on fit, validation or `dev` documents (rule 6).
- Every score from a dry run or a gate is reported per period kind (annual and interim) beside the total (D18).
- Time boxes are estimates. The week has 7 days. The boxes add up to about 6.5 days, leaving about half a day of slack.

## What is cut first if the week overruns

The rule is to cut inside the week (`08-revised-plan.md`). In order:

1. Fuzzy label matching. It is conditional anyway (Task 4).
2. Cash flow statements in mapping and metrics. The plan already names them as the first cut, and the first thing restored if time is left.
3. RapidOCR, if it does not install and run within its part of the box. The bake-off then compares Vision and Tesseract only, and says so.
4. The unit-caveat stage, moved to the start of week 3.

These are never cut: the split, the dry run with its timing, the OCR bake-off and the decline.

### Task 1: Issuer split, override record and scoring log (time box: half a day)

**Brief:** Build the split of `04-execution-phases.md` 2.4. Use SHA-256 of `holdout:` plus the issuer key, modulo 100: buckets 0 to 14 are the holdout, 15 to 29 validation, the rest fit. Add the record of the four overrides, the append-only scoring log and a report command. Both the dry run and the week 3 dataset builder need them.

**Where it lives:** `fra_core.split` in `packages/core`. Its callers are the dry-run harness (`eval/`), the dataset builder (`training/`) and the corpus report (`scripts/`). None of these is a package. `fra-core` is the one workspace package that all three import, and it depends on nothing else in the workspace. `issuer_key` moves there from `scripts/corpus.py`, which now imports it, so there is one key rule. `sec_fsds.py` builds its CIK key with the same `cik_key`. The two records sit beside the corpus files that the split reads: `eval/corpus/holdout_moves.yaml` and `eval/corpus/scoring_log.tsv`. Core does not know where they are: their paths are defined once in `scripts/corpus.py`, beside `CANDIDATES`, and callers pass them in. Since task 2, the records' paths and file format live in `eval/harness/holdout_records.py`. Holdout documents leave `fra_core.split` only through `holdout_for_scoring`, which logs the look first; the report gets counts from `part_counts`, never documents.

**Files:** `packages/core/src/fra_core/split.py`, `packages/core/tests/test_split.py`, `eval/corpus/holdout_moves.yaml`, `eval/corpus/scoring_log.tsv`, `scripts/corpus.py` (the `split` command), `tests/scripts/test_corpus_split.py`, `training/sources/sec_fsds.py`, `Makefile` (`corpus-split`), and pointers in `04-execution-phases.md` 2.4 and `03-repository-layout.md`.

**Tests:**

- The hash is deterministic, with a bucket recomputed by hand.
- A corpus issuer with a CIK lands in the same part as its SEC rows.
- An issuer whose documents carry a CIK on some and not on others is refused.
- A move only goes from the holdout to fit.
- An override is allowed only before the first look. After a look, a move is a spent look.
- The log appends rows in date order and refuses incomplete rows.
- `model_test` and `blind` are refused.
- The report matches the counts in 2.4.

**Done when:** `make corpus-split` prints the counts of 2.4. Each enforced rule is shown to be tested by removing it and watching a test fail.

**Reviewers:** `solutions-architect` (placement across packages), `code-reviewer`.

**Not built here:** recomputing earlier holdout scores without an issuer that leaves after a look. Nothing has been scored yet. That is built with the first spent look, if one happens.

### Task 2: First dry run on the holdout issuers (time box: 1 day)

**Brief:** Run the full pipeline that exists today on the 35 holdout documents: locate, convert, structure and review. Time each document, and report every score per period kind. The run is a look, so it goes through `holdout_for_scoring`, which writes a `dry_run` row to the scoring log before any document is returned.

**Files:** `eval/harness/dry_run.py` (new). It reads `candidates.yaml`, `holdout_moves.yaml` and `scoring_log.tsv`, and writes its report under `var/eval/dry_run/`. It also needs `tests/eval/test_dry_run.py` and a `make dry-run` target. The target has no pool argument, so it can only select the holdout. The harness becomes the one place that reads and writes the moves record and the scoring log: their file-format code moves out of `fra_core.split` next to it, leaving core with the pure functions.

**Tests (on synthetic records and stub stages):**

- The run refuses `model_test` and `blind` (the refusal comes from `fra_core.split`).
- A failed run still leaves its log row, because the look happened.
- The report carries annual, interim and total for every figure.
- A document that fails is recorded with its failure class and does not stop the run.

**Done when:**

- The report shows, for each of the 35 documents, its time in seconds and its stage outcomes.
- The report gives counts per failure class, each split annual / interim / total.
- The log has one `dry_run` row.
- The time per document is compared with the budget in `08-revised-plan.md` (under 1 minute digital, 2 to 4 minutes scanned). The 24 October plan is flagged for the owner if the measured times say one day is not enough.

**Reviewers:** `ml-engineer` (evaluation design and strata), `code-reviewer`.

**Owner first:** copy or fetch the corpus PDFs into the main checkout (`var/handoff/TODO.md`, section 1). Only 19 of the 35 are in the worktree.

### Task 3: OCR bake-off (time box: 1.5 days, of which 2 hours for `cv2`)

**Brief:** Make `import cv2` work in the Docker image first. Either add the system libraries to `docker/Dockerfile` (`libxcb1`, `libgl1`, `libglib2.0-0`, `libsm6`, `libxext6`), or put `opencv-python-headless` in the lock in place of `opencv-python`. Prefer the headless wheel if docling accepts it, because it keeps the image smaller. Record the image size either way. Then put Tesseract and RapidOCR behind the existing `fra_ingest.ocr.OcrEngine` protocol, beside `VisionOcr`. Score all three on the golden scans with the extraction eval (`make eval-extraction`).

**Files:** `docker/Dockerfile` or `uv.lock`, `packages/ingest/src/fra_ingest/ocr.py` (two engines), `packages/ingest/tests/` (engine contract tests), `configs/ingest.toml` (engine choice per profile), `docs/blueprint/14-run-profiles.md` (results and decision).

**Tests:**

- Each engine returns `OcrLine`s in reading order on a rendered fixture.
- An engine that is not installed raises `OcrUnavailableError`; nothing falls back silently.
- `docker compose run --rm worker python -c "import cv2"` exits 0.

**Done when:**

- A table gives, per engine and per language, the numeric cell accuracy on the scanned golden pages and the time per page.
- The engine for Docker is chosen by that table and recorded.
- If no engine reaches 98.0% on scanned Arabic, R15 and D14 apply: scanned Arabic is native-only and is shown held for review. That is written down.

**Reviewers:** `ml-engineer` (scoring), `solutions-architect` (image and profile), `code-reviewer`.

### Task 4: Label mapping (time box: 1 day)

**Brief:** Map each extracted row label to a canonical item. Use taxonomy aliases in both languages first, then structural anchors: a total's position, its sum relations from the review stage, and the statement it sits in. Add fuzzy matching only if a critical item is still unmapped on `dev` or fit documents once aliases and anchors are in. The critical items are revenue, net profit, total assets, total equity, total current assets and total current liabilities. A row that maps to nothing is flagged, never guessed (Gate B: no silent wrong mapping).

**Files:** `packages/ingest/src/fra_ingest/` (a mapping module beside `label_match.py`), `packages/core/src/fra_core/taxonomy/canonical_items.yaml` (aliases), and tests beside them.

**Tests:**

- Arabic and English aliases resolve to the same item.
- An anchor resolves an unlabelled total.
- An ambiguous label is flagged, not mapped.
- Golden Almarai English and Arabic map to the same items.

**Done when:** every critical item on the `dev` documents is mapped or flagged in both languages. Unmapped labels are listed by failure class on fit documents only.

**Reviewers:** `ml-engineer` (mapping accuracy), `code-reviewer`. Add `solutions-architect` if the mapping contract changes `fra_core`.

### Task 5: Analytics (time box: 1.5 days)

**Brief:** Create `packages/analytics` (`fra_analytics`), depending only on `fra_core`. It has three parts:

- Identity checks: assets = liabilities + equity, and the subtotal ties, with the D6 tolerance.
- About 12 metrics, using the D1 to D6 defaults (zero and negative denominators, period handling for interim statements by D4 and D5).
- The unit-caveat stage, which carries scale and currency caveats into every metric.

Every number traces to cells or to a formula over traced values.

**Files:** `packages/analytics/` (new workspace member), its tests, `pyproject.toml` (workspace, test and type paths), `docs/blueprint/03-repository-layout.md` if the layout differs.

**Tests (first, from hand-computed values):**

- Each metric on a small statement, including each D1 case.
- An identity that holds within tolerance and one that fails.
- A caveat that reaches a metric.

**Done when:** the metrics compute on the golden Almarai statements, with each value traced, and the identity results agree with the review stage.

**Reviewers:** `solutions-architect` (new package and its dependency direction), `code-reviewer`.

### Task 6: Decline banks and insurers with a reason (time box: half a day)

**Brief:** A document whose industry verdict (`fra_ingest/industry.py`) is a bank or an insurer ends in a decline with the reason, not in statements. Negative controls in fit and validation carry `sector` in `candidates.yaml` to test against.

**Files:** the stage that ends a job (`fra_ingest/stage.py` or the review stage), and tests.

**Tests:**

- A bank verdict gives a decline with its reason.
- A corporate document is not declined.
- An uncertain verdict goes to `needs_review`, not to a confident decline.

**Done when:** every negative control in fit and validation ends in a correct decline or `needs_review` with a reason. The holdout's one negative control, Pioneers Holding, is checked only in the next dry run, not opened.

**Reviewers:** `code-reviewer`.

**Done when:** the note gives Gates A and B on `dev` and on both dry runs, per period kind, with counts measured by script. It also lists the open failure classes and where each will be fixed (never on a holdout document).

**Reviewers:** `ml-engineer`, `code-reviewer`.

## Decisions that may come up

- **No OCR engine reaches the scanned gate on Arabic.** R15 and D14 already say what follows. Nothing new to decide, but the demo needs to say it.
- **A dry-run failure that cannot be reproduced on any other document.** The issuer leaves the holdout as a spent look (`holdout_moves.yaml`, `kind: spent_look`). Earlier scores are recomputed without it. That recomputation is built then.
- **Checkpoint length,** from the measured time per document (Task 2).
